# OpenAI 图片插件 WebUI 布局与图库性能改造设计

**日期**：2026-05-11  
**插件名**：`astrbot_plugin_openai_image`  
**范围**：仅修改插件目录 `data/plugins/astrbot_plugin_openai_image/` 内的网页后台相关实现，不改动 AstrBot 框架本体。  
**设计基线**：采用已确认的 `方案 A（平衡工作台）`。

---

## 1. 背景与目标

当前插件网页后台已经具备生图、编辑、历史图库与本地缩略图缓存能力，但仍存在以下问题：

- 生图页与编辑页的结果区视觉层级偏弱，控制区不够贴近底部工作台形态。
- “生成结果 / 编辑结果”标题占用可视空间，结果预览区域不够集中。
- 历史图库当前会一次性请求并渲染全部图片，图片越多越容易带来首屏卡顿、滚动压力与多余网络请求。
- 历史图库使用普通网格时，横竖比例差异较大的图片容易留下明显空隙。
- 结果区与历史图库没有统一的“按图片尺寸动态排布”规则，横图无法自然跨列展示。

本次改造目标如下：

- 将生图页与编辑页重构为“上结果、下控制”的紧凑工作台。
- 把结果区升级为统一的四态状态容器：空状态、生成中、成功、失败。
- 在结果区与历史图库统一使用按图片尺寸动态跨列的流式布局。
- 将历史图库升级为“懒加载 + 自动分页加载 + 轻量虚拟滚动”。
- 允许用户在设置界面中自定义历史图库每页数量，且只保存在当前浏览器本地。

---

## 2. 用户确认结论

以下结论已经与用户确认，作为本次实现的硬约束：

- 生图页与编辑页都采用统一布局策略。
- 结果区位于上半部分，目标高度约占工作区的 `60% - 70%`，本次按约 `65%` 设计。
- 控制区位于下半部分，并贴近页面底部，排列紧凑。
- `生成图片 / 编辑图片` 按钮与提示词同行，位于提示词输入区域左侧。
- “生成结果 / 编辑结果”不再保留重标题，改为轻量状态标签或直接省略。
- 结果区必须覆盖四种完整状态样式：`empty / loading / success / error`。
- 历史图库需要自动填补上下图片之间的间隙。
- 结果区与历史图库都要根据图片尺寸动态调整展示方式，横图允许跨两列。
- 多图生成采用流式展示：每生成出一张就立刻插入结果区，而不是整批完成后一次性出现。
- 历史图库分页采用滚动接近底部时自动加载下一页，不保留手动“加载更多”作为主路径。
- 历史图库每页数量只保存在当前浏览器本地，不写回服务端配置。

## 3. 范围与非目标

### 3.1 本次范围

- 调整网页后台内嵌 HTML、CSS、原生 JavaScript 结构。
- 调整历史图库接口，支持分页、筛选、排序与必要的图片尺寸元数据。
- 增加历史图库本地浏览设置项。
- 增加结果区与历史图库的动态布局逻辑。
- 补充与网页后台相关的测试。

### 3.2 非目标

- 不引入新的前端框架。
- 不改动 AstrBot 框架核心页面、核心接口或通用管理台。
- 不把“每页数量”同步到插件服务端配置。
- 不实现复杂的多端同步设置体系。
- 不重构现有 IndexedDB 缩略图缓存体系，只在其基础上优化触发时机。

## 4. 整体方案

### 4.1 页面布局策略

生图页与编辑页统一采用 `方案 A（平衡工作台）`：

- 上半部分为结果区，承载状态展示与本轮结果预览。
- 下半部分为控制区，承载提示词输入、按钮与参数配置。
- 结果区优先展示内容，状态标题轻量化。
- 控制区以“按钮左置、输入右置、参数紧凑分组”为主要结构。

### 4.2 性能策略

历史图库不再走“全量元数据 + 全量缩略图”的模式，而是改为：

- 服务端分页返回元数据。
- 前端仅保留视口附近的页面内容。
- 图片卡片进入视口附近后才触发缩略图加载。
- 保留浏览器本地缩略图缓存，优先命中缓存，避免重复下载。

### 4.3 布局统一策略

结果区与历史图库统一使用“按图片尺寸决定卡片跨度”的规则：

- 横图优先跨两列。
- 竖图保持单列，但卡片高度更高。
- 方图使用标准卡片尺寸。
- 无法获取尺寸时先按默认卡片展示，避免异常数据阻塞渲染。

## 5. 生图 / 编辑工作台设计

### 5.1 结构分区

每个工作台页面统一拆成以下两层：

1. `workspace-result-panel`
   - 用于展示当前任务状态与本轮输出结果。
2. `action-panel`
   - 用于展示提示词、主按钮、尺寸、质量、数量、审核或参考图等控制项。

结果区目标高度约 `65%`，控制区约 `35%`。在窄屏下自动改为纵向堆叠，但仍保持“结果优先、控制靠下”的阅读顺序。

### 5.2 提示词与主按钮布局

主按钮移动到提示词同行左侧，布局形式如下：

```text
[生成图片/编辑图片按钮] [提示词输入区域]
```

设计意图：

- 让主要动作入口始终稳定出现在用户视线左侧。
- 缩短“输入提示词 -> 点击生成”的操作距离。
- 让控制区顶部直接呈现“先操作，再调参”的节奏。

### 5.3 参数区布局

按钮与提示词下方为紧凑参数区：

- 生图页：数量、尺寸、质量、审核。
- 编辑页：尺寸、质量、参考图上传/粘贴区域。

参数区使用紧凑网格，避免大面积留白，保持操作密度。

## 6. 结果区状态设计

结果区统一采用状态机渲染，覆盖以下五个前端阶段：

- `idle`
- `submitting`
- `streaming`
- `success`
- `error`

其中视觉状态对外归类为四种：

### 6.1 初始空状态 `idle`

- 浅灰背景。
- 虚线边框。
- 居中提示“暂无结果”。
- 可附带轻提示，引导用户输入提示词并点击按钮开始生成。

### 6.2 生成中状态 `submitting`

- 蓝色主题氛围。
- 显示旋转加载动画。
- 主按钮禁用，避免重复提交。
- 在尚未返回第一张图前，结果区整体保持等待状态。

### 6.3 流式生成状态 `streaming`

- 本质上仍属于“生成中”，但已开始展示部分结果。
- 第一张图返回后立即插入结果区网格。
- 后续返回的图片继续增量插入，并按最新图片尺寸动态重排。
- 视觉上保留轻量蓝色状态提示，表示任务尚未结束。

### 6.4 成功状态 `success`

- 切换为绿色主题反馈。
- 使用自适应图片网格展示所有本轮结果。
- 不要求固定列数，列数由容器宽度与图片跨度共同决定。

### 6.5 失败状态 `error`

- 切换为红色警告主题。
- 显示明确错误提示文字。
- 保留再次提交的入口，不额外要求复杂恢复机制。

## 7. 结果区图片布局设计

### 7.1 动态跨度规则

结果区图片布局与历史图库共用一套跨度判定规则：

- 当 `width > height * 阈值` 时，判定为横图，优先跨两列。
- 当 `height > width * 阈值` 时，判定为竖图，保持单列但使用更高的卡片高度。
- 其他情况按方图或近方图处理。

阈值不写死到配置项中，先作为前端内部常量维护，便于调试。

### 7.2 流式插入行为

多图生成时，每次 API 调用完成后立即将结果插入本轮结果列表：

- 第 1 张图返回：结束纯等待态，进入流式展示态。
- 第 2-N 张图返回：继续插入网格。
- 最后一张图完成：整体状态切换为 `success`。

这样既满足“边出图边可见”，又不需要改后端为真正的 HTTP 流式响应。

## 8. 历史图库性能改造设计

### 8.1 分页加载

历史图库改为服务端分页模式，不再一次性获取全部图片元数据。

前端行为：

- 初次进入图库时请求第一页。
- 当底部哨兵节点进入预加载范围时，自动请求下一页。
- 当前页加载完成后，如 `has_more = true`，允许继续滚动触发下一页。

### 8.2 懒加载

历史图库中的图片缩略图只在卡片进入视口附近时才触发加载：

- 先渲染占位卡片。
- 进入视口附近后优先检查 IndexedDB 缓存。
- 无缓存时再请求对应图片资源并生成缩略图。

这样可显著减少长图库下的初始缩略图请求数量。

### 8.3 轻量虚拟滚动

不引入复杂虚拟列表库，而采用“窗口化分页虚拟化”：

- 保留当前视口附近的若干页真实 DOM。
- 离视口很远的旧页只保留高度占位，不保留图片节点。
- 用户滚回去时再恢复该页 DOM。

该策略更符合当前原生 JS 页面结构，实施风险低于逐节点绝对定位式虚拟化。

### 8.4 自动补缝布局

历史图库使用支持 `grid-auto-flow: dense` 补位的流式网格布局：

- 横图优先跨两列。
- 竖图单列高卡片。
- 方图标准卡片。
- 通过网格自动回填空位，尽量消除上下缝隙。

## 9. 历史图库接口设计

### 9.1 查询参数

`GET /api/images` 扩展为支持分页与查询参数：

- `limit`：每页数量。
- `cursor`：下一页游标。
- `keyword`：搜索关键字。
- `type`：文件类型过滤。
- `sort`：排序方式，首期支持 `latest / oldest / name`。

### 9.2 返回结构

返回体设计如下：

```json
{
  "images": [],
  "next_cursor": "opaque-cursor-or-empty",
  "has_more": true
}
```

### 9.3 图片元数据字段

每个图片项在现有字段基础上增加：

- `width`
- `height`
- `aspect_ratio`

设计意图：

- 前端可提前计算卡片跨度。
- 可在图片尚未实际加载前生成更稳定的占位骨架。
- 降低因图片加载完成后尺寸变化导致的布局跳动。

### 9.4 宽高读取策略

宽高信息优先从图片文件本身读取。

若读取失败：

- 该图片项仍然返回。
- 尺寸字段允许为空或为默认值。
- 前端降级到默认卡片，不让异常文件阻断整页接口。

---

## 10. 搜索、筛选与排序设计

当前搜索、类型过滤、排序会作用于整个历史图库数据集，因此改为服务端查询更合适。

前端行为如下：

- 用户修改搜索词、类型或排序项后，重置当前图库状态。
- 清空已加载分页数据。
- 从第一页重新请求。
- 重新建立底部哨兵与虚拟滚动窗口。

这样可以避免“只在当前已加载片段中筛选”的错误体验。

## 11. 本地设置设计

### 11.1 设置项

在设置界面新增“历史图库每页数量”配置项。

建议提供：

- 若干预设值，例如 `20 / 40 / 60 / 80`
- 或允许输入自定义正整数

### 11.2 存储位置

该设置只保存在当前浏览器本地，例如 `localStorage`。

设计原因：

- 这是偏浏览体验的本地偏好，不需要影响其他访问者。
- 避免为单一前端体验项增加服务端配置负担。
- 与现有本地缓存设置的性质一致。

### 11.3 生效方式

用户修改每页数量后：

- 立即保存到本地。
- 立即重置图库分页状态。
- 重新从第一页按新页大小加载。

### 12.1 结果区状态

结果区状态：

- `idle`
- `submitting`
- `streaming`
- `success`
- `error`

### 12.2 图库状态

图库状态：

- `initial-loading`
- `ready`
- `page-loading`
- `empty`
- `error`

设计意图：

- 首次加载与翻页加载分离，避免 UI 误判。
- 即使某次翻页失败，也保留已加载内容，避免整页闪空。

## 14. 风险与控制

### 14.1 主要风险

- 图片宽高读取若实现不当，可能引入额外依赖或增加接口耗时。
- 虚拟滚动与 dense 布局叠加时，若占位高度估算不稳，可能出现滚动跳动。
- 流式结果插入与历史图库刷新同时发生时，需要避免状态互相覆盖。

### 14.2 控制策略

- 优先采用最小改动，在现有原生 JS 与内嵌 HTML 架构内演进。
- 宽高读取失败时允许降级，不以尺寸字段为接口硬依赖。
- 虚拟滚动先按分页窗口实现，不一步走到最复杂的逐卡片绝对定位方案。
- 结果区与图库状态分别管理，避免公用单一 loading 标志。

## 15. 验收标准

满足以下条件视为本次设计目标达成：

- 生图页与编辑页都呈现“上结果、下控制”的工作台结构。
- 主按钮位于提示词左侧且同行显示。
- 结果区具备空、加载、成功、失败四种明确样式。
- 多图生成时每张图片返回后能立即出现在结果区。
- 历史图库不再一次性加载全部元数据与全部缩略图。
- 历史图库支持自动分页加载。
- 历史图库图片进入视口附近后才触发实际加载。
- 历史图库与结果区都支持横图跨两列。
- 历史图库空隙明显减少，展示更紧凑。
- “每页数量”能在设置页配置，并仅保存在当前浏览器本地。

## 16. 实施顺序建议

建议按以下顺序实施，降低联动风险：

1. 先补测试，锁定新布局结构与分页接口契约。
2. 改后端图库接口，补分页与尺寸元数据。
3. 改结果区状态机与工作台布局。
4. 改历史图库前端分页、懒加载与轻量虚拟滚动。
5. 接入本地设置项与手工验证。
